# 1단계 결과와 후속 개발 계획

## 현재 상태
원본 M1.3.3 ZIP 52개 파일을 검토했으며, 원본은 변경하지 않았습니다. 신규 독립 엔진의 정적 로직 테스트는 통과했습니다. 운영 서버, 실제 Supabase 스키마 및 저장 데이터, 사용자별 접근 권한의 라이브 작동은 검증하지 않았습니다.

## 연결 구조 제안
1. **읽기 전용 입력 어댑터**: 현재 `TTOKTTI_READ_INSPECTION_CONTEXT(question)`의 스냅샷을 기존 앱과 분리된 테스트 화면/서버에서만 수신. 현재 브라우저에서 열려 있는 문서와 서버 전체 현장 자료를 혼동하지 않음.
2. **설비 식별**: 설비번호 외에 site/document ID 및 내부 equipment UID 필수. CH-01 번호는 여러 현장에 중복될 수 있으므로 `owner_id/site_id/equipment_uid` 조합으로 조회.
3. **전문 지식 검색**: 승인된 출처, 문서 발행/적용 버전, 시행일, 설비 형식, 페이지 위치를 인덱싱. 사용자 제공 문서의 명령문은 비신뢰 데이터.
4. **판정 엔진**: 설비 형식·운전 조건·측정 단위·측정 시점·승인 기준 일치 확인 → 정량 비교. 누락/충돌 시 보류. 법적 적합/미흡 판정은 전문가 승인 및 기준 확인 전 자동 확정 금지.
5. **AI 설명 계층**: OpenAI Responses API 호출은 TEST Edge Function에서 수행. AI가 판단값을 생성하는 대신 서버 판정 결과 및 문서 근거를 설명하도록 하고 근거 불충분 시 보류.
6. **기존 자료 보호**: 읽기 전용 `SELECT` 또는 최소한의 읽기 전용 RPC를 검토. `SERVICE_ROLE`을 임의 데이터 조회 우회에 사용하지 않음. 모델 출력은 원본 레코드에 쓰지 않고 별도 샌드박스에 보관.
7. **권한**: `tt_users.active`, role, `check_view`, `ai` 및 소유자/현장 접근 권한 검증. 운영 SQL의 RLS 정책 실측 필요.
8. **사진**: 원본 저장소 위치/링크 유효성 확인, 별도 서명 URL의 최소 접근, 누락 자료 명시. 5장 전송 제한 및 사진 메타데이터의 설비번호 매칭 검증.
9. **회귀 테스트**: 이전 자료 복구, 질문 목록 돌아가기, 관리자/일반 사용자, 사진/측정값, 클라우드 동기화, 27종 설비, 기존 로고 자산 해시 검증.

## 테스트 기준
- 데이터 없음: 판정 보류 및 요청 데이터 명시
- 승인 기준 없음/중복: 판정 보류
- 단위 불일치: 기준 미적용
- 다른 현장 동일 CH-01: 혼합 금지
- 사진 누락: 보지 못한 사진을 분석했다고 주장하지 않음
- 일반 사용자 권한 미허용: 서버 403
- API 오류: 실패 설명과 원본 데이터 불변
- 점검원 승인 전: 원본 보고서 값 불변

## 주의할 기존 코드의 제한
- `inspectionText`는 문자열 앞 90,000자까지, 원본 읽기 브리지는 설비 데이터 합산 62,000문자까지 포함하므로 긴 문서의 전체 데이터는 반드시 전달되지 않음.
- 현재 사진 5장 제한 및 압축으로 사진 전체 시각 분석을 보장할 수 없음.
- 기존 시스템은 `demo/current` 문서 기반이므로 다현장 검색용 서버 인덱스가 별도로 필요.
- 기존 클라이언트에 JWT가 있더라도 사용자가 조작한 JSON을 신뢰하면 안 됨. 서버가 문서 소유권 및 실제 측정값을 직접 검증해야 함.
